# 计量与判读

## 固定问题和部署

| 目标 | 本次回答的问题 |
|---|---|
| 固定请求集吞吐 | 同样的请求与输出策略，成功交付多少 token，整批用时多久，质量和时延是否满足约束？ |
| 固定到达负载体验 | 对同一到达表，实际发送有多大滞后，端到端时延、错误率及满足质量/SLO 的有效产出如何？ |
| 受约束容量 | 在质量、时延、错误和资源边界内，哪个到达率或并发区间可持续？还需验证持续供给、稳定窗口和队列趋势。 |

实验前固定端点与实例、请求集与实际子集、tokenizer/模板、seed、到达/并发和采样策略。记录部署配置、实际加载的包/源码与模型身份、预热状态、工具版本和运行次序。变更前声明质量判据、每个场景的主指标/保护项、最小收益及预算。未知项可以随探索结果交付，正式判定需要相应证据。

## 有效输出和完整时间

`X_out = N_Y / T`，单位 token/s。按以下口径从原件复算。

- **分子**取最终成功请求的实际输出 token 之和。内置采集器使用服务端最终 `usage.completion_tokens`。核对 EOS、停止、reasoning/特殊 token 的计数语义，同时报告实际输出长度分布。缺失用量保留 unknown，失败请求的部分输出不计。请求上限、输入、chunk、padding、重算或多 rank 副本均不能补账。
- **分母**取同一客户端单调时钟上的完整批次墙钟秒数。服务就绪、预热和排空在计分前完成。内置窗口从启动工作线程前持续至全部请求处理和客户端收尾完成，包含等待、失败和窗口内编译。每个请求都要有终态。其他稳态窗口须另定跨界归属和删失规则。
- **质量和成功分别记录**。通过传输和协议校验的输出仍需任务质量评估。结果保留输入、输出分布、停止原因和失败率，便于识别长度变化带来的吞吐差异。
- **goodput** 用同一个整批墙钟 `T` 作分母，分子累加终态成功且同时满足逐请求质量、TTFT 上限和 E2E 上限的请求最终输出 token。在正式比较中，两个时限按场景事先声明，含等号，缺少 TTFT 的请求不计入合格分子。默认计时从实际发送开始、首输出含推理通道、计数取服务端最终完成 token。可在正式规则中冻结开环计划到达、仅可见内容首字及端点显式提供的内容 token 计数。该指标可用作护栏或主指标，也可与原主指标并列，分别核验最小收益。批次级质量和尾延迟仍独立核验。[正式验收契约](../../references/round_evidence.md#按逐请求-goodput-验收)

正式比较前，质量判定须覆盖本次实测输出，并绑定配置、请求集和输出原件；核对质量报告引用与校验报告的 `source_hashes` 指向同一组 run 原件。预检质量通过只是开始采集的条件，正式输出未核验时保持待确认。

## 客户端时延与负载

- `TTFT = first_output_ts - send_start_ts`，取有首个非空 content/reasoning 载荷的成功请求。`E2E = end_ts - send_start_ts`，取全部成功请求。保留样本数，p50/p99 按排序后 `(n−1)p` 线性插值。小样本尾分位需要注明样本量。
- 采集器同时记录收到结束原因、最终用量和完成标记的客户端时间戳。它们用于[流式长尾诊断](../../diagnose/references/stream_tail.md)，正式 E2E 与批次墙钟使用完整窗口。缺少新字段的历史运行照常复算。
- 开环把计划到达到实际发起的滞后单列。从计划到达计时的业务可在逐请求 goodput 契约中选 `latency_origin=planned_arrival`，并用 `send_lag_p99_s` 或 `send_lag_max_s` 核验实际发压迟滞。客户端逐请求新连接、线程上限、Python 解码和原件写盘均可能限制发压。并发上限与实际在途数分别报告。
- 全部请求在 `[send_start_ts, end_ts)` 上的在途数积分，等于各请求逗留时长之和。除以 T 得平均在途数。`X_req = 成功请求数 / T`。按同一系统边界和请求群体解释，客户端在途数本身不能揭示服务端队列深度。
- SSE 记录载荷事件，一次事件可能携带多个 token。内置工具可报告 TTFT、E2E 和发送滞后，无法直接测逐 token ITL、引擎实际 batch 或内部瓶颈。若另报 TPOT，须说明时间端点、分母和样本范围，例如只有 O>1 且首末输出齐全时才有 `(last−first)/(O−1)`。

## 比较与交付

1. **核验资格。** 比较计划与实际差异、质量报告和生效证据。在同一场景固定工作负载、环境、计量契约、采集器和实际客户端策略，所有场景测试同一个基线部署 A 和同一个候选部署 B。源码/构建对照按 [实现契约](tool_contract.md#源码或构建产物对照) 声明两侧实现身份并固定服务配置；环境变化仍会被拒绝。并发扫描描述负载特性，要验证服务改动分别比较 A@c1 与 B@c1、A@c4 与 B@c4。正式计分关闭 profiler，诊断 run 单独留存。
2. **独立重复。** 先观察基线波动，再按预定配对/交错顺序运行两侧。完整 run 是重复单位，按波动与最小可辨收益规划数量，记录全部样本及环境变化。仅按事先规则或独立污染证据标记异常。用配对效应、区间及逐项约束判定，不把单次峰值、组中位数之比或单个 run 的请求数当作独立重复证据。搜索多个候选后以未参与挑选的新运行确认胜出者。
3. **判定与交付。** 计量有效、两侧配置生效、任务质量通过、所有主指标的效应区间下界超过约定最小收益、全部场景的 SLO 和其他保护条件逐项通过，且完成所需独立确认时，才建议采纳。报告列出各场景的实际结果、不确定性、未决项和建议理由，附原件与派生报告的路径/hash、运行顺序、实际用量、退出码及部分产物。有事前预测和独立观测时单列机制证据。计量无效、协议失败、保护条件超限和证据不足分别说明原因与下一动作，由协调者决定采纳、补证或实际回退。
